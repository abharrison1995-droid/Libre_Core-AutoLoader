Archiso `_unshare` mapping shape
-------------------------------

The pinned Archiso helper uses `unshare --map-auto --map-root-user --
COMMAND` for non-root operations. The corresponding no-write command under
the exact privilege drop and route-free namespace was:

    setpriv --bounding-set=-all,+setuid,+setgid --reuid=1000 --regid=1000 --clear-groups -- unshare --map-auto --map-root-user -- sh -c 'id; cat /proc/self/uid_map; cat /proc/self/gid_map; grep -E "CapEff|CapPrm|CapBnd|CapAmb|NoNewPrivs" /proc/self/status; ip -j route show'

It exited zero and reported UID/GID 0 inside the new namespace, maps
`0 1000 1` and `1 100000 65536`, no routes, and NoNewPrivs 0. The elevated
capability sets in that child are scoped to its user namespace. This confirms
the mapping shape only; it is not an ISO build result.

`arch-chroot -N` mapping, mounts, cleanup, and route inheritance
---------------------------------------------------------------

A minimal scratch root was prepared with `/usr/bin/true`, `/usr/bin/bash`,
`/usr/bin/readlink`, `/usr/bin/ip`, and their runtime libraries. The exact
command shape was:

    setpriv --bounding-set=-all,+setuid,+setgid --reuid=1000 --regid=1000 --clear-groups -- /usr/bin/arch-chroot -N /mnt/archv1/work/chroot-test /usr/bin/bash -c '/usr/bin/readlink /proc/self/ns/net; /usr/bin/ip -j route show'

The warning that the fixture directory was not initially a mountpoint was
expected; arch-chroot's setup self-binds it. The child reported
`net:[4026532219]` and `[]`, then exited 0. A preceding and following
mountinfo hash matched exactly. The fixture's `/dev`, `/proc`, `/sys`, `/run`,
and `/tmp` mount targets had no remaining children after the command, and no
UID-1000 processes remained. A first earlier attempt before adding the
`/usr/bin/true` fixture reached chroot execution but exited 127 because that
binary was absent; it is superseded by the successful run above.

An artificial second `unshare --fork --pid --mount --map-auto ...` invoked
inside an outer PID+user namespace failed opening `/proc/1/uid_map`. This is
not evidence against the pinned execution path: Archiso's helper operations,
`pacstrap -N`, and `arch-chroot -N` are launched as sibling one-level user
namespaces when the trusted outer launcher creates only a network namespace.

`pacstrap -N` false-success defect
----------------------------------

The exact installed `/usr/bin/pacstrap` belongs to arch-install-scripts
31-2 and has SHA-256
`c0cbe2eb3e77a2a4437b03021ec1e63f31f20888778cd3c70ff49d2368371207`.
The generated script has no `set -e`; lines 295–305 run the `-N` unshare child
and then run an unconditional `rm "$tmpfile"`.

In the route-free namespace, a deliberate no-repository/no-package probe ran
with stdout and stderr redirected to a regular log file, then captured the
command's status immediately (no pipeline):

    setpriv --bounding-set=-all,+setuid,+setgid --reuid=1000 --regid=1000 --clear-groups -- /usr/bin/pacstrap -N -C /dev/null -M -G /mnt/archv1/work/pacstrap-probe-final autoloader-no-install-probe >/tmp/pacstrap-probe.log 2>&1
    result=$?

Observed `result` was `0`, while the log contained:

    error: no usable package repositories configured.
    ==> ERROR: Failed to install packages to new root

The target contained no local package records. The host mount table stayed at
the hash above, the disposable mount targets had no residual children, and no
UID-1000 process remained.

As a status-propagation control, the same exact privilege drop ran:

    setpriv --bounding-set=-all,+setuid,+setgid --reuid=1000 --regid=1000 --clear-groups -- unshare --fork --pid --mount --map-auto --map-root-user --setuid 0 --setgid 0 -- bash -c 'exit 7'

The immediate return status was 7. Thus the observed zero is specific to the
generated pacstrap 31-2 script's error path, not util-linux unshare generally.
This is a release-blocking false-success condition. Production builds remain
closed until a hash-verified operation-owned pacstrap overlay preserves the
child status and passes its negative-exit, cleanup, and mkarchiso integration
tests, or an independently verified corrected upstream pin is available.

No `mkarchiso`, candidate ISO, QEMU boot, or physical workflow was run for
these probes. Hardware validation remains pending.
